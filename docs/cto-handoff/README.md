## 必须连同历史一起保留的业务校准

1. **先创作可用，再谈平台成熟。** 第一阶段提供原文/场次/资产/状态资料；后续要交付有导演内容、适合实际生成、用户读得懂的分镜脚本。资料完成、代码测试、网站上线均不替代成品认可。
2. **15/30两模式预先选择。** 在内容合理、可生成、不改稿的前提下默认尽量接近所选上限，短单元要有具体戏剧/换场/组合/容量理由。不能只摘“上限非必须填满”而丢掉长连续偏好，也不能靠无用空镜/拖慢/删词硬填。
3. **生成单元不等于内部镜头。** 长连续可以有快切、甩镜和多个人物的先后反应；不要把长单元拍成呆滞的一镜到底，或把每个短反应镜拆成一次独立生成。
4. **情绪贯穿各专业。** 观众体验、人物目标/阻力/策略、表演/空间、摄影光影、声音和编排需要共同保留情绪升级。不是前置写了“惊讶”就完成，更不能由保真约束取消合法的导演增强。
5. **稳定性与高张力一起解。** 场内名单、单元参与、实际可见和主动主体分开；旧项目1–2主动主体控制有用户来源，不能未经讨论整条撤销。用观看顺序、声画分工和差异反应控制同帧负荷，不靠删戏或七人同时清晰表演。
6. **锁稿与可改稿分流。** 不擅改原词、归属、事实、关系和结果；允许的影视增强不等于新增关键剧情。原稿事实、解释/创作候选、采用的版本与批准范围分开。
7. **省Token不是缩成品。** 省重复读写、无关上下文、无用管理与返工，保留必要时长、动作、表演、光影、对白声音及衔接。专业岗可读完整必要片段，只改有权范围。
8. **JSON是手段，不是质量。** 结构化底稿、有限改区及确定性校验有价值；具体schema、调用粒度和最终栏目没有因此全部获批。用户版/Seedance版应与内部版本/证据/调度信息分层。
9. **51是失败反例。** 用户明确拒绝七单元成品。其原句映射或两处方位文字修正只能证明相应局部事实，不能恢复它的精品/合格样本地位；本包不附真实剧本或完整案例稿。
10. **区分执行证据。** 高管示范、普通员工复现、真实目标CLI/API、视频实测和用户认可分别记录。不假定API拥有本机文件/长期会话/工具；不靠偷偷换更强模型、加费或代写掩盖能力差距。

后续如用户给出更具体的新决定，应带来源和适用范围更新相应现行文档；不能只向旧历史不断追加“最高优先级”，也不能因本次归档静默重跑生产。
