# 原项目 Sites 复刻设计

## 目标

以 `/Users/yue/Documents/CL` 为唯一产品与界面基准，把原项目部署为公开 Sites 应用。保留原页面、文案、样式、导航和业务含义；不再用当前 Runner 控制面替代主页。Sites 负责网页与 D1，本地 Runner 只负责无法在 Sites 中执行的 CLI/本地命令。

## 页面与访问

- 原样恢复 `/login`、`/`、`/projects/new`、`/projects/[projectId]`、`/projects/[projectId]/episodes/[episodeId]` 及原有导出接口。
- 复用原项目组件和 `globals.css`；仅替换数据库、认证和本地执行适配层，不重新设计界面。
- Sites 保持公开链接。网页使用原项目自己的账号会话，不使用 ChatGPT 登录。
- `/runner` 保留为设置页，从原应用账户生成设备配对令牌；Codex 登录只发生在运行 Runner 的电脑上。

## 数据

- 将原 SQLite 的 21 张业务表及现有数据完整迁入 D1，保留原 ID、关系和账号归属；`runner_tokens`、`runner_jobs` 作为额外控制表保留。
- 以 D1 作为网页数据源。建立与原 Prisma 调用语义对应的仓储层，页面组件不直接感知 Drizzle/D1。
- 原有 5 个测试账号、会话规则和项目隔离继续有效；密码明文不进入源码或迁移文件。
- 迁移后逐表核对记录数，当前旧库基准总量为 4568 条。

## 执行数据流

1. 普通增删改查直接写 D1，并立即在原页面显示。
2. API 模式由 Sites 通过服务端 HTTP 调用原 API Provider，并按岗位/阶段把结果持续写入 D1；不经过 ChatGPT 或本地 Runner。
3. CLI、文件系统和本地脚本操作写入 `runner_jobs`。
4. Runner 使用配对令牌领取本人任务，在本机执行原脚本，回传经服务端校验的结构化变更，再由 Sites 写入 D1。
5. 页面明确显示“等待 Runner / 执行中 / 已完成 / 失败”，Runner 离线时不再表现成无响应。
6. CLI 模式只要求 Runner 所在电脑完成 Codex CLI 登录，不把网页账户与 ChatGPT 账户绑定。

## 分段交付

第一段先完成原页面 1:1 恢复、应用账号登录、全部 D1 表与旧数据迁移、项目新建后可进入、项目详情和剧集详情可浏览及普通编辑。第二段再逐个接通原 CLI/API 执行按钮与 Runner 结果同步。每段只改适配层，不重新设计产品。

## 错误处理

- 无权限项目返回不可见，不共享匿名浏览器数据。
- Runner 离线或任务失败时显示明确状态和错误，不创建无反馈按钮。
- 尚未接通的执行功能必须明确禁用并说明原因，不伪装为可用。
- 数据迁移失败时保持旧库只读不变，不删除或覆盖旧数据。

## 验收

- 无痕窗口打开公开链接不出现 ChatGPT 登录。
- 使用原应用账号登录后，只能看到该账号项目。
- 首页、新建项目、项目详情、剧集详情的结构和样式以原项目为准。
- 新建项目后自动进入项目详情页。
- 21 张业务表记录数和关键关系与旧库一致。
- Runner 离线时任务显示等待状态；上线后可领取并回传结果。
- 构建、自动化测试和上述关键浏览器路径通过后再发布。
