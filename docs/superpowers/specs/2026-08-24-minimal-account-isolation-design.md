# 最小账号登录与项目隔离设计

## 目标

在不改变现有工作流和整体视觉风格的前提下，为私有测试版本增加五个预置账号。用户必须登录后才能使用工作台，并且只能读取和操作自己名下的项目。

本方案只服务于五台设备的私有测试，不作为未来公开注册系统的完整方案。

## 已选择方案

采用数据库内的预置用户名、密码哈希和服务端会话：

- 账号固定为 `tester01` 至 `tester05`，私有测试期使用同一个临时初始密码；密码只在部署时通过环境变量提供，不写入源码或 Git 文档。
- 初始化脚本通过未提交的环境变量接收初始密码，只保存密码哈希，不输出明文密码。
- 使用现有 `User`、`ProjectRole` 关系表达项目归属。
- 使用新增的数据库会话记录和安全 Cookie 保持登录状态。

未选择的方案：

- ChatGPT 账号白名单：需要准备五个外部账号，不适合当前设备隔离测试。
- 共用密码或设备访问码：不能真实验证不同用户的数据隔离。

## 功能边界

本轮包含：

- 登录、退出和三十天会话保持。
- 五个预置测试账号。
- 项目列表、详情、修改、删除、归档、导出和现有 API 的服务端归属校验。
- 创建项目时自动绑定当前账号。
- 将升级前的现有项目归属到 `tester01`。
- 在现有工作台显示当前账号和退出入口。

本轮不包含：

- 注册、邀请、找回或修改密码、邮箱验证、双重验证。
- 项目共享、成员管理或管理员后台。
- API Key、第三方 Cookie、Codex 登录信息的保存。
- 本地 Runner、桌面 GUI、在线数据库迁移或 Sites 发布。

## 数据模型

### User

沿用现有 `User`，增加：

- `username`：唯一、忽略大小写使用，登录和界面展示均使用标准化的小写值。
- `passwordHash`：自描述密码哈希字符串，包含算法、工作因子、随机盐和摘要。
- `failedLoginCount`：连续失败次数，成功登录后清零。
- `lockedUntil`：连续五次失败后锁定十五分钟。

现有必填邮箱使用 `tester01@accounts.invalid` 至 `tester05@accounts.invalid`，不提供邮件能力。

### Session

新增 `Session`：

- `id`
- `userId`
- `tokenHash`：唯一；数据库只保存随机会话令牌的 SHA-256 摘要。
- `createdAt`
- `expiresAt`

退出时删除对应会话；读取到过期会话时视为未登录并清除 Cookie。

### ProjectRole

继续使用现有 `ProjectRole`：

- 五个测试账号都可以创建项目；新建项目后，该账号在该项目内拥有 `ADMIN`，可以执行当前版本的全部项目操作。
- 新项目创建事务同时写入当前用户的 `ADMIN` 项目角色。
- 项目列表通过 `roles.some.userId = currentUser.id` 过滤。
- 任意项目入口都必须再次验证该用户存在对应 `ProjectRole`，不能只依赖列表过滤或前端隐藏。
- 升级脚本只给尚无任何角色的旧项目补充 `tester01 / ADMIN`，可重复执行且不会制造重复记录。

## 密码与会话安全

- 密码使用 Web Crypto 可执行的 `PBKDF2-HMAC-SHA-256`，工作因子为 600,000，每个账号使用独立的 16 字节随机盐。
- 密码比较与令牌比较使用恒定时间比较。
- Cookie 名为 `director_session`，设置 `HttpOnly`、`SameSite=Lax`、`Path=/`；生产环境同时设置 `Secure`，有效期三十天。
- 会话令牌使用密码学安全随机源生成 32 字节；浏览器持有原令牌，数据库只持有摘要。
- 登录错误统一显示“账号或密码错误”，不暴露账号是否存在或是否被锁定；锁定期内仍返回同一错误。
- 登录成功后只允许跳转到本站相对路径，防止开放重定向。

当前弱临时密码只允许用于私有测试，公开访问前必须更换。未来公开注册前，需要单独重新评估托管身份服务、密码找回、邮箱验证、MFA、风控和审计。

## 服务端授权边界

建立两个统一入口，替换当前可信请求头方式：

- `requireSessionUser()`：读取 Cookie、查询有效会话并返回当前用户；页面请求未登录时跳转登录页，API 请求返回 `401`。
- `requireProjectAccess(projectId)`：先取得当前用户，再通过 `ProjectRole` 查询项目；无权访问与项目不存在统一按 `404` 处理。

不再从客户端请求头读取全局角色。创建项目只要求已登录；其余权限由该用户在目标项目中的 `ProjectRole` 决定。

以下位置都必须调用统一入口：

- 项目库和归档项目查询。
- 项目、分集和执行日志页面。
- 所有会修改项目数据的 Server Action。
- 提示词、导出、任务包等 API 路由。
- 启动、停止、重跑和清空流水线的入口。

已通过授权入口创建的内部后台任务可以继续使用 `projectId` 工作，但不得新增无需会话即可从公网触发的执行入口。

## 登录与界面流程

1. 未登录访问工作台时跳转 `/login`，并保留安全的本站内返回路径。
2. 登录页只显示用户名、密码、登录按钮和通用错误提示。
3. 登录成功后优先返回原访问页面，否则进入项目库。
4. `AppChrome` 侧栏底部显示当前 `testerXX` 账号和“退出登录”。
5. 退出后撤销当前会话并返回登录页。

登录页复用现有 `globals.css` 的画布、玻璃表面、蓝紫主色、边框、字体和按钮语言；不建立第二套设计变量，不调整现有工作台布局。

## 错误处理

- 数据库不可用：登录页显示“暂时无法登录，请稍后重试”，不输出底层错误或哈希信息。
- Cookie 缺失、损坏或会话过期：按未登录处理，不抛出页面错误。
- 越权项目访问：页面和 API 均按项目不存在处理。
- 初始化脚本重复运行：保留既有账号和密码；只有显式旋转参数及新的环境变量密码同时提供时才更新哈希，并撤销该账号全部会话。
- 创建项目时若项目角色写入失败，整个创建事务回滚，禁止产生无主项目。

## 验证方案

### 自动测试

- 密码哈希、验证、错误密码和不同随机盐。
- 会话生成、摘要查询、过期和退出撤销。
- 非本站返回路径被拒绝。
- 未登录页面跳转、未登录 API 返回 `401`。
- 用户只能列出自己拥有角色的项目。
- 用户不能查看、修改、归档、删除、导出或执行其他账号的项目。
- 新项目与当前账号角色在同一事务中创建。
- 旧项目只迁移给 `tester01` 一次。

### 五账号验收

1. 五个账号分别在五个浏览器或设备登录。
2. 每个账号创建一个名称可辨识的项目。
3. 每个账号的项目库只显示自己的项目。
4. 用其他账号直接访问项目 URL、调用修改或导出入口，均得到不存在响应且数据不变化。
5. 退出、会话过期和错误密码锁定符合设计。
6. 登录页和账号入口与现有工作台视觉一致，桌面和移动宽度均可正常使用。

## 完成标准

- 未登录用户不能读取任何项目内容。
- 五个测试账号的数据在所有页面、操作和 API 层均相互隔离。
- 明文密码、会话令牌和未来 API 凭证均不进入源码、Git 或业务日志。
- 原有项目工作流与视觉结构保持不变。
- 现有发布验证、账号隔离测试和生产构建全部通过。
