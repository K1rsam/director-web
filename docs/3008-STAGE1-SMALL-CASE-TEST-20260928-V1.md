# 第一阶段小案例实测与成本审计 V1

测试时间：2026-09-28 04:28:21–04:29:28（北京时间）。

## 结论

**目前是“来源保存、分集和轻量目录可运行”，还不是成熟的“标准洗本后可稳定交给第三阶段”。**

真实生产链返回 COMPLETE，两集交接均返回 READY；但同一产物交给现行第三阶段接收器，第一集出现两处对白歧义，被模型调用前的检查拒绝。第二集可以构造请求，尚未调用分镜模型。这不是整体通过，也不是源文丢失。

此前新增的 standard-script、series-direction、semantic-judgment 是独立基础模块，尚未接入这条生产链。本次没有手工补齐新模块产物来掩盖这一差距。

## 4. 需要先完善的地方

### A. 最关键：保真保存不等于标准化接收

原稿：

```text
林岚（压低声音）：
你刚才说：“借你一天：明早还我。”
现在又催？
```

应作为林岚的一段对白，保留“压低声音”、原句、引号内冒号及源片段对应关系。当前第三阶段实际提取为：

```json
{"speaker":"你刚才说","quote":"“借你一天：明早还我。”","cue":""}
```

“林岚（压低声音）：”和“现在又催？”被报告为两处无法安全识别。原句没有从保存的正文里删除，但不能进入稳定制作。接收器最后阻断了调用，没有让错误对白直接进入分镜模型。

原因并非缺少一次“AI自检”：当前P1只定块归属，不产出明确对白节点；资料索引与第三阶段分别用自己的冒号规则猜说者。Q1修好的场次名单不能自动修好其他解析器。

应接通统一的标准正文节点：明确 speaker、channel、cue、textAssembly/sourceRefs。原句由程序复制组装；未知归属按坐标退回，不要求AI重新抄整稿。不能只为本例新增“你刚才说”黑名单。

代码位置：[来源事实猜测](../lib/foundation-facts.ts:47)、[下游对白反抽](../runtime/storyboard-v4/core/source.mjs:84)。

### B. “资料完成”和“可派单”必须分开

本次第一阶段 COMPLETE、documentReady=true、两集handoff READY且reasons=[]；第一集下游仍不能构造任务。现有READY实际更接近目录/资料完成，不证明正文语义已正确接收。

应将同一套“正文结构、说者/声道、来源保真、必要连续性、辅助资料”检查用于交接预览和派单前。不把目录齐全包装成端到端就绪，也不删除第三阶段现有阻断保护。

代码位置：[交接状态](../lib/light-foundation-reader.ts:29)、[网页准备状态](../lib/storyboard-service.ts:37)、[最终拒绝歧义](../runtime/storyboard-v4/core/core.mjs:128)。

### C. 纠错要共享，不能一处修好、另一处仍错

Q1已纠正场次名单，但交接facts仍将“第一集”“出场人物”“你刚才说”标为UTTERANCE/角色主张。这些是程序生成的检索提示，不是AI新增剧情；然而它们同时增加噪声和误读风险。

应从同一个已验结构派生场次、人物、事实索引与接收包，不再各自重猜。事实分类提示不能升级为已确认事实。

### D. 身份与展示名分开，连续性不靠完整名称匹配

资产名是“铜钥匙（蓝色钥匙扣）”，正文是“带蓝色钥匙扣的铜钥匙”。现连续性筛选按完整name、竖线前名称或alias匹配，因alias为空，priorStates漏掉钥匙。前一场原文与本集钥匙资产仍保留，本集又明确发生交接，所以尚不能推断生成必然出错。

应使用稳定实体ID/规范名称与已确认别称，展示名附加外观不影响关联；状态要区分“上一时点持有”与“本集交接后”。不要把历史状态永久沿用，也不靠机械补一堆状态摘要解决。

陈叔在characters里但只有VO，属于字段含义不充分，不代表已经生成实体入场镜头。后续应区分可见出场者与声音参与者。

代码位置：[连续性名称匹配](../lib/light-foundation-supply.ts:97)。

### E. 全剧方向卡尚未接线

原文中的“都市轻喜、克制暧昧、不能把承诺变成恶意捉弄”被保留为backgroundCandidates，未成为跨集同版确认方向。应接入已建的精简全剧卡流程；不能把任意背景句自动宣布为用户已确认，也不能让每集重新定全剧基调。

另有一个配置一致性问题：新建说明仍写GPT6-low，真实执行是Terra/medium，旧验收脚本也硬断言旧配置。下一轮应统一显示和运行配置来源，避免用户误判模型与成本；本次没有顺带修改它们。[旧说明](../app/projects/new/project-create-form.tsx:56)、[实际配置](../lib/role-runner.ts:65)。

## 5. 无效信息与重复上下文

### 不是“生成了很多无用长文”

本例F2只交5项精简目录，Q1只交实际变更，没有生成全剧梗概、逐集总结、重复原文或无意义自评。第二阶段自动形象生成未开启。**主要浪费候选在输入侧，而非本例产出长度。**

保留来源证据、必要造型状态、资产稳定ID和历史回执仍有价值。不能因为当前第三阶段尚未读取某项设计，就认定它对第二阶段出图无用。

### 已量化的三个热点

1. **岗位规则与schema偏重。** F2规则+schema约5,704字符，Q1约8,251字符，均约占各自业务请求六成。payload中还各有803字符固定解释。本例没有已定决定/待办，却仍携带完整回执说明。宜按岗位、生成/修复模式和实际已有待办选取协议，先删除F2不消费的Q1回执要求；必要的“发现新不确定性”出口仍须保留，不能因为本例未用humanChoices就一刀切删掉。
2. **第一阶段内部已压缩，下游交接却恢复了重复索引。** F2/Q1已经使用事实表压缩，省略可由完整源文重建的机械索引。P4交接及第三阶段模型请求没有沿用该传输策略。第一集facts为6,841字符，第二集5,538字符；两集current的7/6条全部同时存在于sourceFactIndex，背景候选与unlinkedBackground也重复一份元数据。第二集原文仅178字符，实际可构造的分镜请求确实携带全部5,538字符facts，不只是数据库占空间。
3. **小判断仍启动完整CLI环境。** 三次63,008输入Token远高于2,015输出。先测清调用环境的固定开销，再评估P1明确结构由程序处理、疑难小题走可替换判断接口、必要创作才使用生成模型。Jev尚未业务校准，本次未调用；不能现在宣称已省下确定比例或让它自动放行不确定结果。

F2/Q1的876字符source、591字符scenes、1,127字符facts在本例重复读取；其中Q1独立核对原文属于必要冗余，不能为省Token删掉后让它只相信F2。Q1本例确实纠正了名单并补了有作用的水渍状态，不建议现在直接取消。

已有[模型输入压缩器](../lib/foundation-model-input.ts:51)可作为接收投影基础，但只能在**当前请求实际包含完整对应原文**时省略可重建项。第三阶段按工作包裁切后，历史/包外证据不能盲删。规范证据保留，模型只收到本次需要的投影；本次尚未实施，也没有以字符压缩冒充实际Token节省。

## 6. 推荐推进顺序与复测条件

1. 先把P1的明确分型计划接到标准正文编译器，打通分行对白、说者/声道、标题/资料分离；场次和事实索引共用结果。
2. 统一交接与派单检查；把本例失败坐标前移到第一阶段呈现，不让用户到了第三阶段才遇到问题。
3. 补实体关联、声音参与者、连续性边界与全剧方向确认。输出保持精简，不让第一阶段代做分镜。
4. 再做规则条件化与模型传输投影。用同一小样本比较真实用量、耗时、输出正确性和下游接收结果；不因Token更少就接受漏事实。
5. 这一例正确后，再补少量异格式/反例：同一行多说者、多个冒号、空行/CRLF、导演备注、缺集号、同名人物、非相邻集。格式变体先零模型验证，有语义差异再用有限真实调用。

本次完成的是**一个真实基线测试与问题定位**，不是第一阶段成熟认证，不证明长剧规模、API路径、并发、超时恢复、素材质量或最终分镜艺术质量。保留V1，后续实质变更再新增V2或追加事件，不覆盖本次失败记录。

测试工具：[有调用上限的真实入口](../scripts/probe-stage1-live.ts)、[不调用模型的结果分析](../scripts/analyze-stage1-probe.mjs)。默认入口只准备隔离数据；显式`--live`才发起新模型调用。重跑会生成新的独立记录，不覆盖本次。
