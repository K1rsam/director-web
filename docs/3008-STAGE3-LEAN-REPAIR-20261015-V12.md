# 第三阶段无损待修运输 V12

本记录追加在 V11 及八十集测试报告之后，不替换旧结论。目标是降低局部返修的重复阅读负担，不改创作 Skill、不删除必要证据，也不重新购买已完成稿。

## 1. 查明的放大原因

可解析、可寻址的待修 JSON 仍放在 `previousDraft.rawText` 字符串内，旧运输器无法为其中坐标提供同一命名空间，因而让整个请求退出短编号运输。结果不只是待修稿变长：来源、历史事实和 Schema 也一并回到长编号。多候选场景还会同时携带候选全文和拼接全文。

这解释了部分“局部问题、整包变厚”，但不等于所有返修或历史增长只有这一个原因。

## 2. 本轮实际改动

- 新捕获规则使用 `model-coordinates-repair-v3`；冻结 V1/V2 的任务保留原协议，不升级原付费请求。
- 仅处理自有的 `previousDraft` 与 `supplementalCandidates` 包装。能证明等值的 JSON 全字段保留为 `parsedRawOutput`，`rawText` 指向该完整对象，不再重复序列化。
- 多候选拼接须逐项证明与原拼接相同，才使用完整对象引用列表；不把候选改为已采用稿，不删除包身份、状态、正文或未知元数据。
- 仅省去 JSON token 间格式空白；字符串内的空白、换行、冒号及所有创作内容保留。旧 `Rxxxx` 字面号预留，避免和新映射碰撞。
- 不透明文本、重复键、替代转义、旧编号绑定、已有保留标记、不一致 previousPlan 或畸形候选包装，均保持原输入；新表示加说明后并不更短时也不采用。
- 原始回包、回执、采用稿、源文和旧请求不变。所有输出仍按本次映射还原长编号，原保真、材料、费用、依赖与停止线保护不放宽。

没有新增生产岗位、审稿模型、重试循环或外部服务。
