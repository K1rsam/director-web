# 3008 自动修复与重复请求检查

日期：2026-09-14。检查目标是通用工作流，不针对某个人物或剧本写特例。

## 现场状态

9-14-3 在北京时间 12:03:14 首次发出 Q1，12:08:58 返回并保存。此前两批 F2 分别覆盖1–29集和30集，没有重复覆盖；两个F1请求内容指纹不同。审计结束时自动修复为0次，状态PARTIAL / BLOCKED，原因是作者资料用途未明确。没有证据表明这次运行在同一问题上自动循环。

## 发现与修复

1. **问题换说法被当成进展。** 旧pendingSignature包含problem；UNRESOLVED preparation.note会进入problem。现在按问题对象、责任方、字段和实际集场范围比较待处理单元，忽略说明文字、待办ID和选择revision变化。只有真正减少且没有新添/转移问题才继续；宽集范围缩到实际子场可识别为进展。仅改写说明的控制器测试在第一次REPAIR后停止，不再付第二次修复。

2. **缺少处理回执绕过修复上限。** 真实离线控制器复现：建议处理/确认采用两类事项，初次执行加两轮REPAIR后仍无receipt，但其他待办已关闭；此时连续4次普通继续，各再发一次EDIT/APPLY_DECISION INITIAL，修复计数一直为2。旧上限只覆盖currentTodos，没有覆盖未完成回执。现将缺回执纳入续作上限，并把已完成修复轮次存入运行证据；删除任务记录再重建，也不能把同一轮修复当成全新工作。两类回归均达到上限后0新增调用，包括连续4次删除任务记录的测试。

3. **长集自己使自己的完成缓存失效。** 旧代码先用修改前场信息写片段依赖，再保存场修改。真实回归证明刚完成的片段立刻被标记changed。现将片段的修改后依赖与场补丁、工作稿在同一事务中保存；新保存的片段不会因自己的修改在下次继续时重做。真实新来源/新决定改变依赖时，受影响片段仍需重新处理，不能全局关闭失效判断。

## 保留的边界

- 自动修复默认最多2轮、累计3次修正调用；格式修复最多1次，并计入累计额度。上限不包含正常初次提取/核对。
- 相同付费响应优先恢复；UNKNOWN不自动重发，避免重复计费。
- 无实际进展时提前停止，不等额度耗完；不伪造“已采用”回执、删除问题或改原文来通过。
- 暂停是止损，不代表底层问题已自动解决。结构诊断仍保留供维护处理；未声称所有剧本以后都不会遇到新问题。
- 本次没有重启3008或干预正在运行的用户worker；已经启动的worker不会热替换其已加载逻辑。新调用/恢复使用更新后的代码。
