# 发布架构与选项

## 当前事实

现有应用可以稳定本地运行，但不能原样部署到云端 Worker：

- SQLite 数据库位于本机文件系统；
- CLI 模式依赖本机 `codex exec` 子进程；
- 岗位 Skill 目前已随仓库发布，但云端不能访问用户电脑；
- 当前身份来自请求头或环境变量，不适合开放公网；
- E0–E5 可能是长任务，不能依赖一次浏览器请求始终保持连接。

## 三种发布方案

### A. 本地优先 Beta

用户从 GitHub 安装并在自己的电脑运行网页、SQLite、API/CLI。

- 优点：改动最少；CLI 天然可用；用户数据留在本机。
- 缺点：安装门槛高；没有统一线上账号与跨设备数据。
- 适合：首批内测、验证流程与输出质量。

### B. 混合 SaaS（长期推荐）

Sites 承载网页与控制面，云数据库保存项目和任务；用户安装轻量本地 Runner，通过一次性配对码绑定设备。云端创建任务，Runner 领取任务、调用本机 Codex CLI，再回传结构化结果。

- 优点：网页可在线使用；CLI 仍使用用户自己的电脑和账号；便于多用户、计费、审计与升级。
- 缺点：需要设备配对、任务协议、离线重试、版本兼容和安全设计。

建议边界：

- 云端：账号、项目、任务队列、结果、API 模式、版本策略。
- 本地 Runner：Codex 登录、岗位 Skill、CLI 子进程、停止与续跑、本机日志。
- 通信：短期轮询即可；稳定后再考虑 WebSocket。每个任务必须有幂等键、租约、心跳和可重试状态。

### C. 云端 API-only

Sites 承载完整网页，D1 或 HTTP 数据库持久化，只保留 DeepSeek API，不提供本地 CLI。

- 优点：最容易形成纯在线产品；用户无需安装。
- 缺点：失去 CLI 优势；平台统一承担模型成本、密钥与长任务调度。

## 推荐发布顺序

1. **私有源码仓库**：排除密钥、SQLite、剧本与调试产物；锁定可回滚版本。
2. **本地 Beta**：用真实用户安装包验证 P1–P2、E0–E5、停止、续跑和失败恢复。
3. **Sites 私有预览**：先部署控制面或 API-only 预览，不开放公网。
4. **数据层**：选择 D1（平台内置、迁移直接）或 HTTP Postgres（事务更可靠、运维更多）。
5. **身份与权限**：私有预览可用 Sites 访问策略；公开产品需明确的登录和服务端授权。
6. **本地 Runner**：实现注册、配对、领取任务、心跳、回传、取消与自动更新。
7. **灰度发布**：内部账号 → 邀请用户 → 公开注册；每阶段保留回滚版本。

## 调试分层

- 纯函数：JSON 解析、岗位路由、问题卡坐标、幂等与重试。
- 契约测试：云端任务 JSON 与 Runner JSON 必须版本化并相互验证。
- 假执行器：CI 只跑 fake Codex / fake DeepSeek，不消耗额度。
- 真实冒烟：每个发布候选只运行一个最小 CLI 与 API 请求。
- 端到端：固定短剧本，验证创建项目 → 单岗位 → E0–E5 → 导出。
- 故障注入：断网、Runner 退出、CLI 超时、重复领取、取消、回传重复。

所有日志使用 `request_id / task_id / device_id / stage_code / attempt` 串联；不得记录密钥、完整提示词或用户剧本正文。
