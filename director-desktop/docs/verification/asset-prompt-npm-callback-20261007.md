# 第二阶段批量提示词回包与来源传递修复

## 故障与原因

批量设计已收到 23 份基础资产提示词，但均停在 `received`，7 个来源依赖形象因此被阻断。后续点击复用同一未决任务检查，没有重新发送这 23 个请求。

普通 npm 原生 CLI 的请求快照只写入 `provider/executable`；新引入的独立资产回调校验却要求 `provider/executable/version`。管理安装路径已有预检身份补全，普通 npm 路径遗漏，导致首次正常回包也被误认为身份漂移。

## 修复边界

- 独立资产设计的普通安装同样记录实际预检的原生路径和版本；回调使用原已保存快照。
- 旧两字段回包只能通过唯一已结束批次恢复：原任务时间窗、源版本及 SHA、资产/形象阻断记录、冻结模型/推理强度/原生路径/版本均须匹配。
- 完整输入、规则、schema、原快照字节、接收事件 hash、原始结果、空回执和合法状态继续校验；领域校验和 CAS 提交保持有效。
- 不补写旧快照的版本，不改原 hash/raw；恢复依据另存审计事件。重复采用不产生新任务或模型调用。
- 不改变第一阶段、第三阶段的工作流和 Skill；本次仅设计文字提示词，不触发图片或视频生成。
- CLI 自动升级后，旧两字段回包按原批次冻结的身份和版本核对，而不是要求与今天的版本相同。当前新请求的三字段身份仍严格匹配。
- 视觉事实发布时保留 `sourceSha256`。历史遗漏只从完整验证的 A15 缓存恢复，除缺少的来源摘要和已有展示字段外必须逐字段相同；不重写事实内容。
- 空视觉事实且原引用全是场次格式行时，设计输入补入这些标记所定位场次的锁定正文。原引用和原文保持不变；提示词可引用其中正文，普通美术补足继续单独声明。已有事实请求不增加上下文。
